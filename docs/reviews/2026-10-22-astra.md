I would delay SME onboarding until transaction cleanup and repeat-create handling are fixed. Keep the lock for now—but remove the unlocked-read exception.

## 1. Top five risks before SMEs

1. **Red — Failed transactions can contaminate the next save.** `app/repositories.py:22–37`: `BEGIN` sits outside the `try`; rollback failures leave the connection reusable. Scenario: candidate update succeeds, snapshot fails, rollback fails; the next viewer saves. Snowflake ignores a second `BEGIN` on an active transaction, so that viewer's `COMMIT` can commit the abandoned update without its snapshot. Mock probe confirmed the wrapper permits this sequence. Fix: protect the entire transaction lifecycle; preserve both errors; quarantine the connection whenever transaction outcome is uncertain, before releasing the lock.
2. **Red — Shared-connection reads are not safely isolated.** `app/db.py:37`; `app/repositories.py:114`: viewer A reads History while B's revision is uncommitted, then B rolls back. A sees evidence of a save that never happened—especially problematic when the recovery instruction says "check History." Connector-level concurrency risks also remain. Fix: serialize every operation on this connection, including result collection and connection reset.
3. **Red — Duplicate creation exists beyond fast double-clicks.** `streamlit_app.py:50–76`: search for `zzz`, create `Fresh metric`, then click Save again normally. The filtered-out record is not selected; the populated create form remains. AppTest probe produced IDs `[1, 2]`. A lost commit acknowledgement creates a similar retry hazard. Fix: retain a request token across retries and atomically persist token→result with creation; reset the form after confirmed success even when search hides the result. Button disabling alone is insufficient.
4. **Yellow — Draft preservation is narrower than the UI implies.** `streamlit_app.py:104–112`: only submitted fields are retained, not the change note. Unsubmitted edits can be discarded by widget cleanup on navigation. Fix: explain unsaved-navigation behavior or use server-synchronized draft fields; retain notes with submitted drafts. Do not equate "no stored draft" with "no unsaved edits."
5. **Red — Recovery is not demonstrated.** A Friday mistake discovered Monday exceeds one-day Time Travel. History is not an independent backup. Also `app/repositories.py:17` uses `OBJECT_CONSTRUCT(*)`, which omits SQL NULL fields: a cleared department becomes a missing key, ambiguous across schema changes. Fix: retained recovery copies + restore drill; preserve nulls and snapshot schema versions, with explicit handling for older snapshots.

## 2. DEC-004: retain a broader lock

Keep the lock, covering all shared-connection access. Rare saves and few viewers favor simplicity until measurements justify connection-lifecycle work.
- Doubt 1: the Python connector advertises `threadsafety=2` (shared connections allowed), not independent transactions. Snowflake warns about shared query-context caches, retry counters, last-query-ID races. A plain SELECT does not commit the transaction; it can queue or fail; concurrent driver activity is not thereby harmless. No connector corruption reproduced. [driver guidance](https://docs.snowflake.com/en/developer-guide/driver-connections)
- Doubt 3: the context-managed lock is released on exception unwinding; that doesn't repair the DB transaction. An injected Streamlit `StopException` escaped `except Exception`, leaving only `BEGIN` issued. Cleanup must handle `BaseException`, then re-raise (don't swallow Streamlit control flow). Real interruption needs a yield point; not proven every click interrupts DB calls.
- Doubt 4: runtime docs describe one shared instance, single process; no basis for automatic multi-replica scaling. Maintenance overlap unverified. A separately deployed app or external writer bypasses this lock.
Move to exclusively leased / per-save connections when measured contention is unacceptable or additional writers arrive. **A reader-writer lock does not resolve concurrent driver-state hazards.** Validation needs its own connection immediately.

## 3. DEC-006: sound identity direction, incomplete enforcement

- Green: immutable IDs, loose candidates, explicit duplicate resolution, no automatic merging.
- Yellow — normalization: one persisted normalization rule for promotion and rename; conservative Unicode/case/whitespace; preserve punctuation unless justified. Display names separate.
- **Red before promotion — uniqueness races:** two connections can both observe an unused name and insert it. Snowflake standard `UNIQUE` constraints are [not enforced](https://docs.snowflake.com/en/sql-reference/constraints-overview). Use a DB-serialized write gateway or an enforced-unique name registry, atomically coordinated with canonical writes. The process lock is only a single-writer interim guarantee.
- **Red before serving — Variants vs siblings:** "Paid Accounts including comped" and "excluding comped" cannot be interchangeable PIs selected arbitrarily. If they share an identity, give definitions explicit keys and selection/disambiguation rules; siblings/cousins get separate identities. Oracle's `docs/dictionary.md:26` and `:143` describe conflicting meanings of "Variant"; resolve that spec.
- Yellow — retired names: reusing an old name for a different metric can redirect historical questions. Reserve retired names/aliases by default.

## 4. REL-07: baseline belongs to an editing episode

Refresh on navigation only when confidently clean, rotating widget generation simultaneously. Preserve the original baseline for dirty/submitted drafts; never refresh during submission. `revision_no` is sufficient when every mutation advances it and baselines contain committed data; no current editable-baseline bypass found. Restore operations must invalidate old editor tokens or advance an epoch; `updated_at` is not automatically safer.
Yellow: `app/services.py:66` does duplicate-warning retrieval after commit; if it fails, a successful save appears uncertain. Separate advisory failures from save success.

## 5. Minimum Oracle-cutover gates (each Red until demonstrated)

- Atomic, idempotent promotion (candidate transition, identity, PIs, history together; reject stale/non-open candidates).
- Coherent serving revision: publish definition and PIs together (else new "exclude comped" text + old inclusion SQL).
- Revision-bound validation: a late pass for rev 6 never authorizes rev 7; bind to immutable revision/content.
- Safe, meaningful validation: isolated read-only execution, bounded runtime/results, expected output shape/grain, SME-approved reference answers. Executable SQL can still be wrong.
- Recovery and rollback: tested restore, immutable audit history, explicit serving rollback, editor invalidation after restore.
- Operational evidence: real two-viewer conflict/rollback tests, duplicate-retry tests, identity attribution, request/query correlation, shadow comparison before switching Oracle's source.

## 6. Process

- Change: make merge readiness enforceable — exact commit SHA, passing checks, independent review, live evidence for persistence changes. "Merge before tests" is Red; another prose checklist won't prevent it.
- Drop: mandatory cross-vendor review for every trivial change. Keep independent review for persistence, identity, security, serving. Model diversity is useful, not a correctness guarantee.
